R1 Specification: Self-Hosted Knowledge Platform

2026-09-17

1. Scope and definitions

R1 is a self-hosted release: one Go binary with PostgreSQL, NATS and an in-process OpenFGA, exposing pages, blocks, permissions, publishing, CEL search and MCP through an API, plus a minimal web app for live collaboration. The desktop release (R2) is the same binary packaged with Electron; nothing in R1 is desktop-specific. Every capability is reachable through the API; the web app is one client of it.

Goals

  • Create, edit, move and version pages and blocks through structured APIs; callers never handle CRDT bytes.
  • One primitive, one store, three surfaces: the block is the primitive; Postgres holds everything durable except bytes and an S3 endpoint holds assets, cold snapshots and backups; the surfaces are Documents, Work (both R1) and Canvas (R2).
  • Ship a minimal web app for live collaboration: sign in, open pages, edit blocks together with live cursors, keep working offline, reconnect and converge; sized for 10 concurrent users across 20 docs with several editors per doc.
  • Share a workspace by DID; roles come from a compiled permission scheme; any block can become a permission boundary.
  • Publish pages to public URLs; every block has a permanent URI; work items carry project keys such as KB-123.
  • Query blocks with Google CEL; rank full-text search.
  • Import and export Markdown and MDX with byte-exact round-trip of anything the parser does not model.
  • Expose MCP with OAuth 2.1 and scoped agent tokens that act under a user's permissions.
  • Encrypt every workspace's history and assets at rest with one key per workspace, held by the node; every object in object storage is ciphertext produced by the node.
  • Run on Docker Compose for teams up to 500 users and on Kubernetes for 10K users and 600K blocks.
  • Keep the user in control of the data: open formats only (Markdown, mdast JSON, Loro's open update format), full export of any workspace at any time, self-host as the default deployment, no proprietary lock-in.

Non-goals (R2 and later)

Electron desktop app (R2); the Canvas surface (whiteboards, R2); WYSIWYG rich-text marks and a formatting toolbar (R2; R1 edits Markdown source per block); views, boards and kanban UI; workflows, FSM and governed attribute writes; automations (ECA); comments; folder and git sync; MDX component rendering; spaced repetition; org-mode import; webhooks; node federation; custom domains. Each is designed for in this spec so it lands without breaking R1 clients. Client-held workspace keys are not a later phase at all: a node that cannot read a workspace cannot search it, query it or serve agents, so that is a different product (section 5). Logseq and Obsidian are import and export targets, not the product model: the platform is inspired by them and built clean, open source, with the user owning the data.

2. Architecture and deployment profiles

One statically linked Go server binary contains every service and has no command-line interface: KB_ROLE selects which services a process runs, migrations apply themselves at startup, and every operator action is an AdminService RPC. The minimal web app is embedded in the same binary and served at /app. Self-host on Compose runs one container with KB_ROLE=all; Kubernetes runs the same image as api, sync and worker Deployments; the R2 desktop app runs the same binary as an Electron sidecar with embedded NATS and FGA and a bundled Postgres.

Desktop packaging (R2, design fixed now)

Electron spawns exactly one child, the server binary; the binary owns Postgres (initdb on first run, health checks, graceful stop, crash restart). Postgres binaries ship inside the app for macOS (arm64, x64), Windows (x64) and Linux (x64, arm64), signed and notarized with the app. Postgres runs with shared_buffers=128MB, max_connections=20, fsync=on, listening on a Unix socket only; on Windows it listens on 127.0.0.1 with a per-install bearer token stored at 0600. Data lives in the platform app-data directory as pgdata/<pg_major>/; a major bump triggers dump-and-restore of truth tables and a projection rebuild. The Electron renderer holds a local Loro doc per open page, so editing works offline and the sync RPCs reconcile with the node when online.

3. Data model

Truth is one append-only CRDT log per doc; every other table is a projection that AdminService.Reindex can rebuild from the logs. The schema below is the complete R1 schema; River and OpenFGA manage their own tables in the river and fga databases.

Invariants

  1. The doc log is the only source of truth for content. Blocks, edges, properties, search and access tables are projections.
  2. A write is acknowledged only after its doc_updates row commits; the ack carries the DB-assigned seq.
  3. Updates are immutable. Undo, restore, moves and API writes append; nothing edits the log.
  4. Updates commute; seq exists for cursors, gaps and history, not for merge order.
  5. Block IDs are UUIDv7, assigned once, permanent across moves, boundaries and restores.
  6. workspace_id is the first column of every primary key and index; there are no cross-workspace joins.
  7. Everything above the KeyRing is plaintext. Rooms, the materializer, the indexer and the compactor decrypt and encrypt at the node edge; search, CEL, the Work surface and MCP run on plaintext projections and never touch ciphertext. Nothing outside the node ever holds a workspace key.
  8. A permission boundary is a doc boundary. Blocks inherit access from their doc; docs inherit from their parent doc unless the FGA parent tuple is absent.

CRDT document layout (Loro)

Container Loro type Content
meta LoroMap title, icon, format (markdown or outliner), journal_date, type_id, props: LoroMap (the page block's bag)
blocks LoroTree, fractional index enabled one node per block; node data is a LoroMap with type_id, props: LoroMap, content: LoroText holding the block's Markdown source, portal_doc_id (boundaries), created_at, created_by
root tree root node the doc's root block

A move is tree.move(node, parent, index), a native Loro operation: concurrent moves converge, cycles are impossible by construction, and sibling order is kept by Loro's fractional index, so the application carries no tree-repair logic. Property keys are property-definition IDs, never names. Multi-valued relation properties are a LoroMap<target_id, true> so concurrent adds merge. Snapshots use Loro's snapshot export; compaction uses shallow snapshots to bound history; sync exchanges updates by version vector. Go reaches Loro through its C FFI with CGO in api and worker; a wazero-hosted WASM build is the fallback wherever CGO is undesirable.

A work item is a block whose type extends the shipped base type work (owns_doc = true, numbered = true); task, bug, feature and epic are shipped subtypes and all of them are rows, not code. Any doc-owning type behaves like a page: it has its own doc, its own boundary and its own publication. The page type is the reserved doc-owning type with numbered = false. Keys are allocated on the API path only, which is why SetType and PagesService.Create are the only ways a block becomes a work item.

Physical design

  • doc_updates, doc_snapshots: ALTER COLUMN ciphertext SET STORAGE EXTERNAL. Ciphertext does not compress, so TOAST stores it uncompressed and skips the compression pass on every write.
  • docs, blocks, pages: WITH (fillfactor = 80) so current_seq, indexed_seq and projection updates stay HOT updates without index churn; per-table autovacuum: autovacuum_vacuum_scale_factor = 0.02, autovacuum_vacuum_cost_delay = 2ms.
  • outbox and audit_log are range-partitioned by time (daily, monthly); retention is DROP PARTITION, never a bulk DELETE.
  • doc_updates is pruned per doc by primary-key range in batches of 1,000 rows once a covering snapshot exists; the delete path is index-only.
  • BRIN indexes on doc_updates(created_at), outbox(created_at) and audit_log(at) for time-window scans; B-tree only where lookups need equality.
  • GIN indexes on blocks keep fastupdate = on with gin_pending_list_limit = 8MB; search lives on tsv and substring match on the trigram index, so one block update touches two GIN entries.
  • Every query names its columns (SELECT * fails lint); hot paths use prepared statements through pgx; generated query SQL is parameterized and plan-cached.

Row-level security

Every tenant table has ALTER TABLE … ENABLE ROW LEVEL SECURITY and one policy: workspace_id = current_setting('app.workspace_id')::uuid. The API sets app.workspace_id per transaction from the authenticated request. Migrations run as a separate role that bypasses RLS; the application role cannot. This is defense in depth behind the mandatory workspace_id predicate in every query.

Every principal is a public key expressed as a DID; there are no accounts, passwords or email addresses anywhere in the system. Users prove control of a key, the node issues short-lived sessions, and every other principal (device, agent token, share link) is owned by a user.

5. Encryption and key management

Six rules define encryption in R1; the rest of this section is their consequence.

  1. One key per workspace: XChaCha20-Poly1305 over doc_updates, doc_snapshots and every object in object storage, AAD-bound to workspace, doc and seq. About a hundred lines of Go behind one KeyRing interface.
  2. The node holds the key. It is wrapped to the node's key in workspace_keys; on Compose the node key is a sealed file with a passphrase, on Kubernetes a Secret or a cloud KMS key, on the R2 desktop the OS keychain. Nothing else in the system ever sees a workspace key.
  3. Everything above the KeyRing is plaintext. The materializer decrypts, applies the write, encrypts, commits. The indexer decrypts and writes blocks, block_properties, block_edges and tsv. Search, CEL, the Work surface and every MCP tool run on those tables and never touch ciphertext; they work exactly as they would with no encryption at all.
  4. Devices get TLS, a session and a cache key. The sync room decrypts at the node edge and sends plaintext Loro updates over TLS to a session already bound to the device DID. Locally, the client encrypts its IndexedDB store with a per-device key: a non-extractable WebCrypto key in the browser, safeStorage in the OS keychain in the R2 desktop app.
  5. Rotation is rare. Removing a member is a permission change; they never had the key. Rotation is for compromise or policy: a new version for new writes, a background re-encrypt, done.
  6. Backups are encrypted by the backup tool with a key derived from the node key: pgBackRest's repository cipher on Compose, Barman Cloud SSE-C on Kubernetes.

Not in this design, by decision: client-held workspace keys (a node that cannot read a workspace cannot search it, query it or serve agents, so that is a different product, not a later phase); device recipients in the key ring (10K laptops holding the org key is 10K places it can leave from, plus a rotation on every lost device); OpenBao Transit in R1 (sealed file or KMS until a customer asks); any encryption layer on the wire beyond TLS. Per-object DEKs stay only because they make rotation cheap: one wrap per upload.

Object storage contract

The bucket contains only ciphertext produced by the node or by a backup tool holding a node-derived key; the object store is never trusted with plaintext, whichever product implements it.

  • EncryptedObjectStore is the only package allowed to import the S3 client (aws-sdk-go-v2, path-style addressing); a compile-time lint fails any other import. Every put and get goes through it.
  • Envelope encryption per object: random 256-bit DEK, XChaCha20-Poly1305 over 1 MiB chunks so range reads and multipart uploads work; a 256-byte header carries alg, key_version, purpose and the wrapped DEK. The chunk index is part of the AAD, so chunks cannot be reordered or swapped between objects.
  • Object keys are opaque, {workspace_id}/{purpose}/{uuid}; Content-Type is always application/octet-stream; user metadata carries only kb-env=1. The store learns object counts, sizes and workspace ids, nothing else. No store-side encryption is required or relied on.
  • Backups are the one path the node does not write itself, so the backup tool encrypts before upload: pgBackRest's repository cipher on Compose (client-side), Barman Cloud with SSE-C on Kubernetes (key supplied per request, never stored by the store). Both keys derive from the node key, so losing the node key means losing backups, which is why AdminService.ExportNodeKey exists.
  • Verification: AdminService.Verify samples 100 objects per bucket, requires the envelope header, decrypts and checks the AAD; CI reads raw objects behind every write path (asset, cold snapshot, export, import, backup) and fails on any recognizable plaintext; the desktop filesystem backend runs the same suite.

Store selection: SeaweedFS (Apache 2.0) is the bundled default because MinIO's community edition entered maintenance mode in December 2025 and its repository was archived in April 2026. The S3 API remains the contract, and the object-store suite runs against SeaweedFS, Ceph RGW and AWS S3 in CI so the store stays interchangeable.

Node key custody by profile

  • Compose: the node key is generated at first start, sealed with Argon2id under KB_NODE_KEY_PASSPHRASE, and written to KB_NODE_KEY_FILE; without the passphrase the node refuses to serve.
  • Kubernetes: the same sealed file in a Secret, or KB_NODE_KEY_KMS naming a cloud KMS key that unwraps it at start.
  • Desktop (R2): generated on first run and stored in the macOS Keychain, the Windows DPAPI-protected store, or the Linux Secret Service; never written to disk in plaintext.

Unwrapped key handling

Unwrapped workspace keys live only in process memory, in an LRU with a 10-minute idle TTL, zeroized on eviction. They are never logged, never included in error details, and never sent over NATS. Rooms, the materializer, the indexer and the compactor fetch keys through one internal KeyRing interface, which is the only code path that calls HPKE unwrap.

The honest limits

The index is plaintext inside Postgres. That is the price of search and agents: no design gives both server-side search and zero knowledge, and products that claim both do client-side search over a small corpus. The security statement is therefore exact: history and assets are encrypted with a per-workspace key held by the node; the query index relies on volume encryption; the node is trusted. The browser cache key is only as safe as the disk it sits on, because non-extractable is an API property, not a storage one; on the desktop app the keychain makes it real.

6. Authorization

Authorization is OpenFGA, one store per workspace, with the model generated from a workspace-owned permission scheme; roles are data, not code. Block-level permissions come from making the doc the permission unit and letting any block become a doc boundary.

Permission scheme

The scheme is JSON stored in schemes, versioned, compiled to an FGA authorization model on every change. The default scheme ships with every new workspace and is editable from day one.

Block-level boundaries

BlocksService.Restrict(block_id, inherit) splits the block's subtree into a new doc of kind boundary, writes a portal node in the parent doc, and writes the FGA tuples above. Unrestrict merges the subtree back and deletes the doc. A viewer without access to the boundary receives the portal with the block id only. A page may hold at most 200 boundaries. Cross-page moves of a boundary carry the doc and its grants.

Access projection for queries

doc_access(doc_id, set_id, permission) is maintained from the FGA changelog: a worker tails ReadChanges and, for every affected doc, recomputes the usersets that grant view and edit (project:P#viewer, doc:D#editor, user:U, public). A principal's principal_sets is computed at session start and refreshed on ACL events for its workspace. Explain

7. Write path, sync, projections and events

All writes converge on one append to doc_updates: structured API writes go through the materializer, the web app and other Loro clients push updates through sync rooms, and both feed the same projection pipeline through the outbox.

Structured write (materializer)

  1. Resolve principal, workspace, FGA checks (section 6). Look up the Idempotency-Key; a hit returns the stored response.
  2. BEGIN; SELECT pg_advisory_xact_lock(hashtext(doc_id)) so one writer materializes a doc at a time on this node.
  3. Load the live doc: warm copy from the materializer LRU keyed by (doc_id, current_seq), else doc_snapshots latest plus doc_updates since it, decrypted and imported into a LoroDoc.
  4. Check preconditions against the live doc: if_version == current_seq when supplied; block exists; parent exists; type rules on SetType and SetProperties.
  5. Apply the mutation in one Loro transaction; export the delta as an update from the pre-mutation version vector; encrypt with the current key version.
  6. UPDATE docs SET current_seq = current_seq + 1 … RETURNING current_seq; INSERT doc_updates; INSERT outbox; INSERT idempotency_keys; COMMIT.
  7. Publish the outbox row to NATS after commit (events.<workspace_id>); on publish failure the outbox poller republishes within 1 s.
  8. Respond with version = seq and the doc's indexed_seq.

Multiple nodes may materialize the same doc concurrently; the advisory lock is per node, and correctness comes from the CRDT: two updates produced from slightly different live states still merge. Preconditions (if_version) are the tool for callers who need linearizable semantics, and they are evaluated inside the lock on the freshest state the node has, so a stale node fails the precondition rather than writing on stale data.

Batch semantics

BlocksService.Batch applies up to 500 operations to one page as a single Loro transaction and one doc_updates row: all-or-nothing, one seq, one event with the operation list. Cross-page moves are the exception: one database transaction appends a delete-update to the source doc and an insert-update to the target doc, two seqs, one event.

Sync rooms

  • Purpose: the web app holds a local Loro doc per open page, so editing is offline-first and collaborative at keystroke granularity; SyncService is its transport. Structured API writes remain the path for agents and integrations, which never use it.
  • Wire: SyncService (Open, Push, Pull, Subscribe) is defined in kb.v1 (section 12). Browsers use one WebSocket per tab at /ws/sync, multiplexing docs and carrying SyncFrame protobuf messages. Non-browser clients may use Connect: unary Open, Push, Pull and server-streaming Subscribe. One message set, two transports.
  • Authentication: the first WebSocket frame carries the access token, already bound to the device DID; the room checks can_view on Open and can_edit on every Push; an ACL event for a doc closes the affected subscriptions.
  • Open(doc_id, since_seq) returns the latest snapshot plus updates after since_seq, decrypted at the node edge; hot docs come from room memory.
  • Push(doc_id, client_id, updates[{client_seq, bytes}]): validate the Loro header and size (≤ 1 MB), batch for 20 ms, allocate seqs as the doc's single writer, encrypt, insert one multi-row doc_updates batch plus outbox rows, commit, ack each update with its seq, then fan out one frame per subscriber per 50 ms tick with the batched updates. A duplicate (client_id, client_seq) is acked with its original seq.
  • Pull(doc_id, since_seq) fills gaps; the client calls it when it sees a seq gap and on reconnect before flushing its pending queue. Loro updates commute, so arrival order never matters.
  • Subscribe streams updates and awareness (Loro's ephemeral store: cursor, selection, name, color) with a 30 s TTL; awareness is never persisted or logged.
  • Rooms: with KB_ROLE=all they are goroutines in the single process. On Kubernetes each sync pod owns a slice of a consistent-hash ring published in NATS; Open through the API returns the owning pod's sync_url; room loss rebuilds from the log; a pod change disconnects clients, which reconnect and Pull.
  • Encryption: rooms never materialize a doc; they decrypt outbound and encrypt inbound at the node edge through the KeyRing and send plaintext Loro updates over TLS. TLS is the wire encryption; there is no layer on top of it.
  • Validation: header and size at Push; semantic validation at compaction, where an update the compactor cannot import is quarantined (doc_updates.quarantined_at, alert) and skipped, so one bad client cannot poison a doc.
  • Limits: 20 open docs per connection, 100 pushes/s per connection, 1 MB per update, 100 subscribers per room before a second room replica takes over fan-out.

8. Query engine (CEL)

QueryService.Query compiles a CEL expression over the block projection into one parameterized SQL statement, access-filtered by doc_access, paginated by keyset cursor only: no offset pagination and no total counts exist anywhere in the API. The same environment powers saved views, MCP search_blocks, and the Logseq simple-query translator.

Compilation and safety

  1. Parse with cel-go, type-check against the environment for the project; reject on any unknown symbol with line and column.
  2. Walk the checked AST into a SQL builder; every literal becomes a bind parameter; no string concatenation of user input anywhere.
  3. Cost estimate: count of EXISTS subqueries, regex operators and edges_* aggregations; refuse above 50 units with RESOURCE_EXHAUSTED.
  4. Wrap with the access predicate and SET LOCAL statement_timeout = '2s'; run on a replica when one is configured.
  5. Cache compiled plans by (project_id, schema_version, cel) for 10 minutes.

cel-go alignment

The engine follows the cel-go model exactly: the service defines the environment, users write expressions, parse and check happen once at save time, and the checked AST is what runs. Where we compile to SQL instead of evaluating in-process, the semantics below keep both paths equivalent, and a differential test proves it.

Postgres performance rules

These rules are enforced by the query compiler and by an SQL lint in CI; a query shape that violates them cannot ship.

Rule Why Enforcement
Keyset pagination only; no OFFSET anywhere in kb.v1 OFFSET n reads and discards n rows, so page 100 costs 100× page 1 cursors encode (sort keys, id); SQL is WHERE (k1, k2, id) > ($1, $2, $3) ORDER BY k1, k2, id LIMIT n+1
No total counts by default COUNT(*) over a filtered set scans every match count_mode: NONE (default), ESTIMATE (planner row estimate), CAPPED (count(*) over LIMIT 10001, reported as 10000+)
Group counts for boards in one query one query per column multiplies the scan count(*) FILTER (WHERE …) with the same cap, or LATERAL … LIMIT per group for first pages
Semi-joins for access and edges a correlated subquery per row is O(rows) compiler emits EXISTS / IN (SELECT …); the doc_access filter is set_id = ANY($sets) on its index
Sargable predicates only a function on an indexed column disables the index the compiler never wraps a column, except through expression columns it knows (title_norm, tsv)
Text search through tsv ILIKE '%x%' alone is a scan search() uses the GIN tsv index; contains() uses the trigram index and is refused on strings under 3 characters
Sorts use an index or a bounded sort large sorts spill to disk order_by accepts indexed fields only (updated_at, created_at, typed property columns, _rank) plus the id tiebreak
Statement and transaction limits one bad query must not hold the primary app role: statement_timeout 2 s, idle_in_transaction_session_timeout 10 s, lock_timeout 1 s
Reads on the replica when configured the primary is reserved for writes Query, List* and public routes use the replica DSN; wait_for_seq falls back to the primary
Every generated query shape has a committed EXPLAIN fixture regressions are caught before release CI runs EXPLAIN (ANALYZE, BUFFERS) against the seeded 600K-block workspace and fails on any sequential scan of blocks, block_properties or block_edges

The write side is short by construction: one materializer transaction holds an advisory lock for one doc, performs one UPDATE and three INSERTs, and commits in under 5 ms; nothing else runs inside it.

Explain and validate

Validate(cel) returns type errors and the resolved property and type ids. Explain(cel) (admin) returns the generated SQL with parameters redacted and the Postgres plan summary, which is how slow saved views get diagnosed.

Logseq simple-query translation

The importer translates {{query …}} clauses: (and …), (or …), (not …), [[page]] → refs(page), (task TODO DOING) → props.status in […], (priority A) → props.priority == 'A', (property k v) → props.k == v, (between …) → journal date range, (namespace x) → descendant_of(x), (page-property …) → page-level props, (sort-by …) → order_by. Untranslatable clauses keep the raw text and set view.props.translation = "partial".

9. Markdown and MDX, import and export, publishing

The Markdown engine guarantees that parse → serialize → parse is identity and that serialization is deterministic; anything it does not model survives byte-exact as a raw node. Publishing renders the same block tree to HTML, Markdown or JSON at a public URL.

Engine

  • Parser: goldmark with extensions producing an mdast-compatible AST (the remark ecosystem's node vocabulary), so JSON exported from the API can be consumed by unified/remark tooling unchanged; the web app ships the same rules in TypeScript with a shared conformance fixture set.
  • Dialects, all on by default: CommonMark 0.31; GFM (tables, task lists, strikethrough, footnotes, autolinks); Logseq (key:: value properties, [[page]], ((block)), {{embed}}, {{query}}, #+BEGIN_… org blocks, TODO/DOING/… markers, SCHEDULED:/DEADLINE:, :LOGBOOK:); Obsidian (wikilinks with |alias and #heading, ^block-id, > [!callout], ![[embed]], YAML frontmatter); math ($…$, $$…$$); MDX (import/export, JSX flow and text elements, {expressions}).
  • Storage: a block's content is its Markdown source in a LoroText. The mdast AST is derived from it for rendering, search, edges and properties and is never stored as truth. Loro's rich-text marks are reserved for the R2 WYSIWYG editor.
  • Node kinds the parser models: paragraph, heading(1–6), list item (bullet, ordered, task), code (lang, meta), blockquote, callout, table, math, image, embed, raw (html or unknown), mdx_esm, mdx_jsx_flow, mdx_jsx_text, mdx_expression; inline: strong, em, code, strike, highlight, link, wikilink, blockref, tag, math, footnote_ref.
  • Serializer: one canonical form per node (ATX headings, - bullets, fenced code with backticks, pipe tables with aligned columns, key:: value properties after the first line in outliner format, frontmatter in markdown format). Raw nodes are written back verbatim including surrounding blank lines.
  • Source maps: each block records src_line and a byte span at import time; export writes blocks in tree order.

PagesService.Convert(page_id, format) rewrites meta.format; the tree is unchanged. API-created pages default to markdown. Import chooses outliner only when a file body is a single top-level list, else markdown; the caller can force either.

Import

PagesService.ImportFolder(project_id, upload_id, options) runs as a job and returns a report. Steps: unzip; classify files (.md, .mdx, assets, logseq/config.edn, pages/, journals/, assets/); create property definitions on demand with kinds inferred from values (number, date, checkbox, url, else text; alias, tags → the built-in behaviors); create pages by file name and Logseq namespace rules; create blocks; upload assets with content-hash dedup and rewrite links; honor id:: and ^id as block ids; second pass resolves [[links]], ((refs)) and creates missing pages; translate simple queries; create publications for public:: true when options.publish = true.

The report lists per file: blocks created, raw nodes and their kinds, unresolved links, translated and partial queries, property kind inferences, and any file the parser refused (none by design: a file that fails to parse is imported as one raw block and flagged).

Export

PagesService.ExportMarkdown(page_id, include_children) and ProjectsService.Export(project_id) produce a zip in the same layout the importer accepts (pages/, journals/, work/, assets/, views/), deterministic across runs so two exports of an unchanged project are byte-identical. Every doc-owning block exports as one .md file whose frontmatter carries type: (the type name, e.g. task) and, for numbered types, key: (e.g. KB-123); the importer reads both back, so a round trip preserves work items and their keys. Property ids are written as names; unknown-to-definition props keep their imported key.

MDX policy

MDX nodes are preserved and returned in the block JSON with their raw source. Publishing renders them as a placeholder (<div data-mdx="…">) in HTML and verbatim in Markdown. Component evaluation is code execution and is R2, in an isolated Node render service with a per-workspace component allowlist; nothing in the Go node ever evaluates JSX.

10. MCP

The node ships an MCP server at /mcp (streamable HTTP), authenticated with OAuth 2.1 per the MCP authorization specification (2026-07-28 revision) or with a pre-minted agent token. Every tool call runs as the agent principal and as its owner, is scope-filtered, and is audited. There is no stdio transport and no CLI: local clients on the R2 desktop app use the same HTTP endpoint on localhost.

Scoping and safety

  • Effective permission = agent scope ∩ owner permission, enforced by the double check on every call.
  • search_blocks and get_backlinks apply the same doc_access filter as the API; an agent never sees a block its owner cannot.

  • Rate limit per agent token as in section 4; a burst of failures (10 in 1 min) disables the token for 15 min and emits agent.throttled.

11. Minimal web app

R1 ships one minimal web app whose only job is collaborative editing: sign in, pick a workspace and project, open pages and work items, edit blocks together with live cursors, keep working offline, reconnect and converge. Its navigation is Documents · Work in R1, with Canvas added in R2. It is embedded in the server binary and served at /app, and it is sized for 10 concurrent users across 20 docs with several editors per doc, a small fraction of what the backend supports. Architecture

  • React and TypeScript, Vite build; assets embedded in the Go binary, content-hashed, served at /app with immutable caching; index.html carries KB_PUBLIC_URL and feature flags.
  • API access through Connect-web clients generated from kb.v1, cached with TanStack Query. The web app is one more API client and gets no private endpoints.
  • @kb/sync-client (TypeScript, published for third parties): one WebSocket per tab multiplexing up to 20 docs; per doc a LoroDoc, lastSeq, a pending queue, and an IndexedDB store holding a shallow snapshot every 500 local ops plus the tail; imports are order-agnostic; a seq gap triggers Pull; awareness through Loro's ephemeral store with a 30 s TTL; local pushes coalesce for 50 ms.
  • Rendering: unfocused blocks render through the same mdast rules as the server, kept identical by a shared TypeScript and Go conformance fixture set; the focused block is raw Markdown source in CodeMirror.
  • Encryption on the device: plaintext arrives over TLS and lives in memory while a doc is open; the IndexedDB store is encrypted with AES-256-GCM under a per-device key that never leaves the device — a non-extractable WebCrypto key in the browser, safeStorage in the OS keychain in the R2 desktop app — and is cleared on sign-out. Non-extractable is an API property, not a storage one, so in the browser the cache is only as safe as the disk; on the desktop app the keychain makes it real.

Security

  • Access token in memory; refresh token in an httpOnly, SameSite=Strict cookie scoped to /rpc and /ws; a custom request header on every Connect call defeats CSRF; the WebSocket sends the access token in its first frame, never in the URL.
  • CSP default-src 'self'; connect-src 'self' wss:; img-src 'self' data:; wallet connector libraries are bundled, no third-party scripts at runtime, no analytics.
  • Rendered Markdown passes through the same allowlist sanitizer the publisher uses; raw HTML nodes are escaped.

service SyncService {
  rpc Open(OpenRequest) returns (OpenResponse);              // snapshot + tail since client seq
  rpc Push(PushRequest) returns (PushAck);                   // updates → seqs
  rpc Pull(PullRequest) returns (PullResponse);              // updates since seq
  rpc Subscribe(SubscribeRequest) returns (stream SyncFrame);
}
message SyncFrame {                          // also the WebSocket frame at /ws/sync
  oneof kind {
    Hello hello = 1;                         // first client frame: access token, client_id
    OpenRequest open = 2;  OpenResponse opened = 3;
    PushRequest push = 4;  PushAck ack = 5;
    PullRequest pull = 6;  PullResponse pulled = 7;
    Update update = 8;     Awareness awareness = 9;
    SyncError error = 10;
  }
}
message OpenRequest  { string doc_id = 1; int64 since_seq = 2; }
message OpenResponse { string doc_id = 1; bytes snapshot = 2; int64 snapshot_seq = 3;
                       repeated Update tail = 4; int64 current_seq = 5; string sync_url = 6; }
message PushRequest  { string doc_id = 1; string client_id = 2; repeated ClientUpdate updates = 3; }
message ClientUpdate { int64 client_seq = 1; bytes update = 2; }
message PushAck      { string doc_id = 1; repeated AckedUpdate acked = 2; }
message AckedUpdate  { int64 client_seq = 1; int64 seq = 2; }
message PullRequest  { string doc_id = 1; int64 since_seq = 2; }
message PullResponse { string doc_id = 1; repeated Update updates = 2; int64 current_seq = 3; }
message Update       { string doc_id = 1; int64 seq = 2; bytes update = 3; string actor = 4; }
message Awareness    { string doc_id = 1; bytes state = 2; }   // Loro ephemeral store bytes, TTL 30 s
message SyncError    { string doc_id = 1; string code = 2; string message = 3; }

update bytes are Loro updates as exported by LoroDoc.export({ mode: "update", from }); the room never inspects them beyond the header. sync_url on OpenResponse tells a browser which sync process to connect to on Kubernetes; with KB_ROLE=all it is the node's own URL.

Upgrades

  • Images are tagged by semver; the binary refuses to start against a newer schema than it knows.
  • Migrations are forward-only SQL embedded in the binary (goose library) and run at startup under an advisory lock, so any number of replicas can start together; every migration is tested against a snapshot of the previous release's data in CI.
  • Projections may be rebuilt by a migration through AdminService.Reindex without downtime, because reads fall back to the previous projection until indexed_seq catches up.
  • Rolling upgrades on Kubernetes: worker first, then api, then sync (rooms rebuild from the log; clients reconnect and Pull).
  • Web app assets are versioned with the binary; a stale tab detects the version change on its next request and reloads after flushing its pending queue.
  • Desktop (R2): Postgres major upgrades run dump-and-restore of truth tables, then reindex; the previous data directory is kept until the new one passes a checksum verification.
